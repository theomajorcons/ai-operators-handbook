Reference spine

FAQ & Troubleshooting

The questions operators ask most, answered from the handbook itself, plus a diagnose-first table for when an answer comes back wrong. Every answer links to the lesson that teaches it in full.

Frequently asked

Which model should I pick, and how much "effort" does a task need?▾

Match the model to the job: a quick setting for light, well-shaped work; a stronger model (or more thinking effort) for tangled, multi-step problems. A hard task on a quick setting comes back neat on the surface but thin underneath. When an answer feels shallow, raising the model or effort is one of the first things to try.

Pick the right model
Why do long chats start ignoring what I said at the beginning?▾

A chat has a budget. In a very long conversation the rule or number you set up top gets crowded out by everything since, so Claude drifts. The fix isn't to repeat yourself louder: ask for a handoff summary and start a fresh chat with it pasted in.

Why you hit your limit
What is "context" and why does giving it change the answer so much?▾

Context is everything Claude can see when it answers: your prompt, attached files, the chat so far. Claude can't read your mind or your drive; if it needs a file or a constraint you never supplied, it fills the gap with a confident guess. Most bad answers are really missing context. Attach the thing, state the constraint.

Give Claude the right context
How do I write a prompt that gets what I actually want?▾

Write it like a spec, not a wish. "Make it better" names no target, so Claude aims somewhere, often not where you meant. Say what better means (shorter, warmer, more formal), who it is for, and what shape the output should take. A clear ask is the cheapest quality upgrade there is.

Write a prompt like a spec
What is a Project, and when is it worth setting one up?▾

A Project bundles standing instructions and source files so you stop re-explaining the same background every chat. Set one up when you do a workflow repeatedly against the same material: the instructions and sources carry across chats so each one starts warm instead of cold.

Projects, files, and instructions
What does "memory" remember, and what should I never rely on it for?▾

Standing instructions and memory let Claude carry preferences and facts forward so you aren't restating them. Treat it as convenience, not a vault: put durable, stable preferences there, but don't lean on it for anything you can't afford to have drift or go stale, and never store secrets in it.

Memory and standing instructions
When should I turn on web search or research, and can I trust what comes back?▾

Turn on research when the answer depends on something time-sensitive or outside what Claude could already know. But a search result is a lead, not gospel: check that the tool actually ran, that the source is current rather than a stale copy, and spot-check the claim before you act on it. Research widens what Claude can reach; it doesn't remove your job of verifying.

Research and web search
What are connectors, and what is safe to connect?▾

Connectors let a regular chat reach a tool or account (email, a drive, a system). They are powerful because they act on your behalf, so connect the least that the task needs, confirm what a connector can see and do before you turn it on, and never wire up access you would not hand a new hire on day one.

Connectors in regular chat
How do I run a safe first session in Claude Code?▾

Start read-only and scoped: point it at one project folder, let it read and propose before it writes, and keep a human gate on anything destructive. You review the diff; Claude doesn't get the keys to the whole machine. Safety here is about scope and gates, not trust.

Claude Code: your first safe session
A tool or script read something from outside: how do I stay safe (prompt injection, least privilege)?▾

Treat anything Claude reads from the outside (a web page, a document, a tool's output) as untrusted. Hidden instructions buried in a source can try to hijack the answer (prompt injection): if an answer takes a sudden strange turn right after reading something external, suspect the source. Defend with least privilege: give each tool and script the narrowest access that does the job, and keep a human gate on actions that matter.

Tools, scripts, MCP, and untrusted input
How do I know the output is actually right (verification and evals)?▾

Don't confuse confident prose with correct work. Verify: spot-check numbers and parsed values by hand, re-read the output against what you asked, and for anything you repeat, build a small eval, a fixed set of cases you re-run so you catch regressions instead of eyeballing each time. Trust is earned per task, by checking.

Verification and evals
When should I never paste something as a "source"?▾

Never paste credentials (passwords, API keys, tokens, ID numbers) as a source. Share other sensitive data only when you're authorized, in an approved environment, and trimmed to the minimum the question needs. A source is for giving Claude what it needs to read, not for handing over secrets.

When things go wrong

Troubleshooting a bad answer

A wrong answer is rarely bad luck; it has a cause. Find the symptom, name the cause, make the one change the cause points at, then rerun. Change exactly one thing so you know what fixed it.
