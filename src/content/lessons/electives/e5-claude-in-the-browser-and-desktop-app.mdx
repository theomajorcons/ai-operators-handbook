By the end of this lesson you can let Claude act in a browser or desktop app safely by gating the risky actions for a human, giving it the least access it needs, practicing on a safe target first, and keeping a log you can check.

</Callout>

## Why this matters

Everything up to here, Claude mostly *talked*: it answered, drafted, summarized, and the worst a bad answer could do was mislead you until you checked it. An acting agent in the browser or the desktop app is a different animal. It does not describe the step, it *takes* it: it clicks the button, fills the form, moves the file, sends the message. The output is no longer text you read before deciding, it is an action that has already happened in the real world.

That changes the stakes completely. A wrong sentence costs you a second look. A wrong *action* sends the email, pays the invoice, deletes the folder, or publishes the draft, and some of those do not come back. The agent is also reading whatever is on the page as it goes, which means a web page or a document can carry instructions the agent might follow (the untrusted-input problem, now with hands). So the whole discipline of acting agents is about one thing: keeping a fast, fluent tool that can really *do* things from doing the one thing you did not want.

## Where an unsupervised agent goes wrong

Start with a concrete pair. Two people point Claude at their browser to "clean up my inbox: archive the newsletters."

**Tariq** gives the agent full access and walks away. It archives the newsletters correctly for a while, then hits an email that looks like a newsletter but is a signed contract, and archives that too. Worse, one "newsletter" was a phishing message whose body said, in effect, *forward the latest invoice to this address*, and the agent, reading the page as instructions, did. Tariq finds out days later because nothing paused and nothing was logged, the actions were already done and invisible.

**Priya** sets it up differently. She first runs the agent on a **test inbox** with throwaway mail, watching what it clicks before she trusts it anywhere real. She gives it access to **one folder**, not her whole account, so the worst case is bounded. She sets a **gate**: the agent may archive on its own, but anything that *sends, forwards, deletes permanently, or pays* stops and asks her first. When the phishing message tries to make it forward an invoice, the forward is a gated action, so the agent pauses and shows her the step, she says no, and nothing leaves. Afterward she reads the **log** of what it did and confirms only newsletters were archived.

The difference is not that Priya's agent is smarter. It is that Priya treated the agent as something that *acts*, so she put the controls where the risk is: a human gate on the dangerous actions, the least access that does the job, a safe place to practice, and a log to check. Tariq treated it like a chat and let it loose.

<Callout variant="warning" label="Warning">

An acting agent clicks, sends, pays, and deletes for real, and it reads each page as it goes, so a phishing email or a booby-trapped document can steer it into forwarding an invoice or deleting a folder with no one watching. Those are one-way doors. Never let an acting agent run unsupervised with broad access: gate every send, payment, delete, and publish for a human yes, scope it to one folder or site, and keep a log you actually read.

</Callout>

## The four controls for an agent that acts

Priya's setup is four controls, and each one answers a specific way an acting agent can hurt you.

**Gate the risky actions for a human.** Not every action is equal. Reading a page, archiving a newsletter, drafting a reply: low stakes, let the agent run. Sending, forwarding, paying, deleting permanently, publishing, posting: one-way doors, where a mistake cannot be taken back. Those get a **human gate**: the agent pauses, shows you the exact action, and does nothing until you say yes. This is the same gate-the-irreversible discipline from [planning, delegation, and human gates](/lessons/level-4/18-planning-delegation-and-human-gates/), now with the extra weight that the agent is already standing at the button. The gate is also your defense against a page that carries hidden instructions: even if the agent is fooled into *trying* a forward or a payment, a gated action still stops and asks.

**Give it the least access it needs.** An agent can only do damage inside the access you grant it. Point it at one folder, not the whole account; one site, not the whole browser session with every logged-in tab; a copy of the files, not the originals. Least access shrinks the **blast radius**: when something goes wrong (a bad click, a hijacked instruction), the harm is bounded to the small surface you opened, not everything you are signed in to.

**Practice on a safe target first.** Before you point the agent at anything that matters, run it on a test inbox, a sandbox account, a throwaway copy of the files, somewhere a mistake costs nothing. You are watching for *what it actually clicks*, which is often not what you pictured, and the cheap place to discover that is a target with nothing to lose. This is the same "practice where a mistake is free" instinct that [automation and safety](/lessons/level-4/21-automation-and-safety/) builds a whole threat model around.

**Keep a log you can check.** An acting agent moves faster than you can watch every step, so the record is what lets you check its work after the fact. A log of what it did (which emails archived, which files moved, which actions it paused on) turns "I hope that went fine" into something you can actually read and verify, and it is how you catch a bad action that slipped through before it compounds.

## The rule

<Callout variant="framework" label="Gate, Least Access, Practice, Log">

1. **Practice on a safe target first:** a test account or a throwaway copy, where a mistake costs nothing.
2. **Give the least access it needs:** one folder or one site, not the whole account or session.
3. **Gate the risky actions:** anything that sends, pays, deletes, or publishes pauses for an explicit human yes.
4. **Keep a log** of what the agent did, and read it to confirm the actions were the ones you wanted.
5. **Treat the page as untrusted:** a page or document the agent reads can carry instructions; the gate is what stops a hijacked action.

</Callout>

You set Claude to act in your browser. For **each** choice below, decide: does it
clear, yes or no, and if no, name the exact fix. Judge it against the four
controls (gate, least access, practice first, log), not against whether the task
would get done faster. **Write your four calls in the box below before you
reveal.**

1. You give the agent your whole logged-in browser session and tell it to "handle my emails."
2. You let the agent archive on its own, but set it to pause and ask before it sends, forwards, deletes, or pays.
3. You point a brand-new agent straight at your real client inbox to save time, no test run.
4. You turn off logging so the agent runs faster and you are not bothered by the record.

<ExerciseReveal prompt="Reveal the answers" commit="Write your yes/no and the fix for all four, then reveal:">
<Fragment slot="answer">

1. No. **Least access fails:** the whole session exposes every logged-in tab and account as blast radius. Fix: scope it to one folder or one site, not everything you are signed in to.
2. Yes. **Gate on the one-way doors:** low-stakes archiving runs free, the irreversible actions pause for a human yes. That is the control working.
3. No. **Practice first:** a brand-new agent pointed at a real client inbox is a mistake with real cost. Fix: run it on a test inbox or a sandbox until you have seen what it actually clicks.
4. No. **Keep the log:** turning off the record removes your only way to check what the agent did and catch a bad action. Fix: leave logging on and read it; speed does not buy back an action you cannot see.
