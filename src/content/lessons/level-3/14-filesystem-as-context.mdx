## Why this matters

In the chat window, you hand Claude context by pasting it in. In a tool that reads your files (like Claude Code from the last lesson) you hand it context a different way: by how your folders are *arranged*. A tidy folder tells Claude where everything is. A messy one makes it guess, and a guess is how you get the wrong file edited.

This is the quiet shift Level 3 has been building toward. Once Claude can see your filesystem, your folder structure *is* your prompt. This lesson is about writing that prompt well.

## Your folders are the context now

When Claude reads your files, it doesn't magically know which one you mean. It reads the names, opens what looks relevant, and works from what it finds. So everything that helps a *person* find the right file fast helps Claude too, and everything that would confuse a new teammate confuses Claude.

Picture a folder named `stuff` with files called `final`, `final2`, and `new_final`. A human can't tell which is current without opening all three; neither can Claude. It opens one, guesses it's the right one, and edits the wrong version. The folder didn't give it a map, so it wandered.

Now picture the opposite: clear folders, one topic per file, names that say what's inside, and a short note at the top explaining the layout. Point Claude at that note and it goes straight to the right file and works. Same request, opposite result, and the only thing that changed was the structure.

<Callout variant="mistake" label="Common mistake">

Keeping `final`, `final2`, and `new_final` side by side and expecting Claude to know which is current. It cannot, any more than a new teammate could, so it opens one, guesses, and may edit the stale copy. Name files for their content and archive old versions, so there is exactly one current file and nothing to guess wrong.

</Callout>

## The four things that make a map

Four habits turn a folder from a maze into a map:

- **Clear names.** `budget-2026.md` tells Claude (and you) exactly what's inside; `final2` tells it nothing. Name files by their topic, not their version history.
- **One topic per file.** A file about one thing is easy to point to. A file that's a little bit of everything matches every question and answers none well.
- **A README at the top.** A short `README.md` that says what lives where is a map Claude can read. Point it at the README (or paste it in) and it's the single highest-value file in a messy folder. (Don't assume it's read automatically: a generic `README.md` isn't auto-loaded the way Claude Code loads a project's `CLAUDE.md`.)
- **Archive old versions.** Move outdated files into a subfolder so there's exactly one current version of each thing. Then Claude can't pick a stale one, because there's nothing stale in the way.

And when you ask, **point to the file** if you can: "update `budget-2026.md`" beats "update my budget" every time, because it removes the guess entirely.

## The rule

<Callout variant="framework" label="Give It a Map">

1. **Clear names:** `budget-2026.md`, not `final2`.
2. **One topic per file.**
3. **A README** at the top: what lives where.
4. **Archive old versions** so there is one current file.
5. **Point to the file** when you ask.

</Callout>

## Try it (10 minutes)

Clean up one real folder, ten minutes maximum.

1. Pick a folder with at least ten files.
2. Rename five files so the names describe the topic. Archive older versions into a subfolder.
3. Create `README.md` using `readme-template.md` and fill in purpose and layout.
4. In a Claude Code session or a chat with the README attached, ask: "Where would I find my budget?"
5. Note whether Claude found the right file.
