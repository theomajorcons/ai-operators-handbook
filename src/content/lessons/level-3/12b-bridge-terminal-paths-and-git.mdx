## The terminal, and why it needs to know "where"

A **terminal** is a text window where you type commands instead of clicking. When you type a command, the terminal runs it, but *where* it runs matters. Every terminal is always sitting "inside" one folder, called the **working folder**. A command like "list the files" lists the files *in that folder*, not your whole computer.

That's the one idea that trips up beginners: the tool you install in the next lesson acts on the folder you're sitting in. If you're in the wrong folder, you act on the wrong files. So the first skill is always knowing where you are.

Two commands answer that:

```
pwd           (shows the current folder: "where am I?")
ls            (lists files in it; PowerShell also accepts dir)
```

And two commands move you around:

```
cd name       (go into a folder)
cd ..         (go up one folder)
```

Think of `cd` as walking into and out of rooms. `pwd` is looking at the sign on the door. If a folder name has spaces, wrap it in quotes so the terminal reads it as one name: `cd "my notes"`.

**Opening a terminal:** on Mac, open Terminal. On Windows, open PowerShell or Windows Terminal. On Linux, open your terminal app. The four commands above work the same in all three.

## A safe place to practice

Never learn a new tool on files you can't afford to lose. The fix is a throwaway folder made just for practice:

```
mkdir practice
cd practice
```

`mkdir` makes a new folder; `cd` walks into it. Now anything you do happens inside `practice`, away from your real work.

**When something goes wrong (and it will),** read the error. Errors usually name the problem: "not found" almost always means you're in the wrong folder or misspelled something. Run `pwd` to check where you are and `ls` to see what's actually there. If the message still doesn't make sense, copy it exactly and ask Claude what it means. That's a good use of Claude.

## Git: an undo you can trust

A practice folder protects your *other* files. **Git** protects the practice files from each other over time. It's a tool that saves snapshots of a folder so you can go back to any earlier one. Each snapshot is a **commit**: a saved point you can return to.

The minimal loop is a few commands, run once to start tracking a folder:

```
git init                          (start tracking this folder)
git add hello.md                  (stage that one file by name)
git status                        (see what is staged and what is not)
git diff --staged                 (read exactly what will be committed)
git commit -m "first version"     (save a snapshot)
```

Name the files you want (`git add hello.md`) instead of `git add .`: staging by name keeps stray or unrelated files out of the snapshot. Run `git status` and `git diff --staged` before you commit so you always know what is going in.

**First commit asks "who are you?"** The very first time you commit, Git may stop and ask you to set a name and email. Set them for this practice folder only (leave off `--global`, which would apply to every project on your computer):

```
git config user.name "Your Name"
git config user.email "you@example.com"
```

Using `--global` writes your name and email into Git's history on every repo you touch, including ones you might share, so scope it to the folder while you practice.

**Making a file to track.** `git` saves files, but you create them first. Make an empty file (`touch hello.md` on Mac/Linux, `New-Item hello.md` in PowerShell), open it in any editor, type a line, and save. Now `git status` will show it, and `git add hello.md` can stage it.

After that, as you make changes:

- `git status` shows *what* changed and lists any untracked files.
- `git diff` shows *how* your unstaged changes look, line by line.
- `git restore filename` throws away unstaged edits to one tracked file: your undo for edits you have not committed yet.

The habit that matters: **commit before every big change.** A commit is a point you can return to if the change goes wrong, which is exactly what you want before letting an automated tool edit your files in the next lesson.

One safety rule travels with Git everywhere: **secrets never go in files you commit or share.** Anything you commit becomes part of the saved history and can be shared along with the project, so passwords and API keys stay out of committed files entirely.

<Callout variant="warning" label="Warning">

A secret committed to Git does not go away when you delete the line later: it stays in the saved history and travels with the project the moment you share it. Keep passwords, API keys, and tokens out of committed files from the start, and run `git diff --staged` before every commit to confirm nothing sensitive is going in.

</Callout>

If Git isn't installed, get it from the official source in the setup card above, not from a search result.

## The rule

<Callout variant="framework" label="Know Where You Are, Practice Safely, Keep an Undo">

- **Know where you are:** `pwd` shows your folder, `ls` lists it, `cd` moves between folders. Quote names with spaces: `cd "my notes"`.
- **Practice safely:** `mkdir practice` then `cd practice`, a throwaway folder away from real work.
- **Keep an undo:** `git init`, `git add hello.md` (name the file), `git diff --staged` to check, then `git commit -m "first version"`; then commit before every big change. `git restore filename` undoes unstaged edits to one tracked file.
- **Read errors** and **keep secrets out of commits.**

</Callout>
